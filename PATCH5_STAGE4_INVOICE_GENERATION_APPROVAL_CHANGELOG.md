# Patch 5 — Stage 4: Invoice Generation Timing, Manual Invoice Validation, and Approval Completeness

This stage is a **thin, additive reconcile + gap-fill** on the canonical invoice
system (`drm.product_posting_invoices` + `server/services/invoice-workflow.service.ts`).
It does **not** rebuild the workflow state machine, does **not** implement
invoice → project generation (that is Stage 5), and preserves all current
behavior by default.

Three problem areas were addressed:

- **P6 — Invoice generation timing.** Standardize *when* the 3 default invoices
  for a GM are generated, behind a single config flag, idempotently.
- **P7 — Manual invoice validation.** Enforce a closed invoice-**type** enum (no
  free-text), and restrict who may create a manual invoice.
- **P8 — Approval completeness.** Block HOD/Accounts approval of incomplete
  invoices and record approval/rejection actors + timestamps.

---

## Guarantees preserved

- Default generation timing remains **`ON_GM_CREATION`** — existing GM creation
  flows behave exactly as before.
- Generation is **idempotent**: re-running for the same GM creates **0**
  duplicates (enforced by a partial unique index on `(gm_id, invoice_type)`
  where `auto_generated AND gm_id IS NOT NULL`).
- No invoice → project generation (out of scope; Stage 5).
- The existing transition map and the mandatory rejection-reason rule are
  unchanged.

---

## P6 — Invoice generation timing

- New service `server/services/gm-invoice-generation.service.ts`:
  - `generateDefaultInvoicesForGm({ gmId, event, actorUserId, req })` — creates
    the 3 canonical default invoices (`LISTING_PAGE`, `MINIWEBSITE`,
    `PRODUCT_POSTING`) for a GM, but **only** when `event` matches the
    configured `gmInvoiceGenerationTiming`. Otherwise it no-ops.
  - `generateInvoicesAfterFinalGmApproval(...)` — thin wrapper that fires the
    `AFTER_FINAL_GM_APPROVAL` event. **Dormant by default** (default timing is
    `ON_GM_CREATION`); included so flipping the config later requires no code
    change.
  - Auto-generated rows are stamped with `auto_generated`, `generated_by`,
    `generated_at`, and `generation_event`, and a best-effort audit entry is
    written per created invoice.
- Wired at the 4 existing default-invoice creation call sites as a **best-effort**
  delegate — a generation failure never breaks GM creation.
- Dormant `AFTER_FINAL_GM_APPROVAL` triggers were added at the final GM approval
  surfaces so the alternate timing works the moment config is changed.

See `GM_DEFAULT_INVOICE_GENERATION_RULES.md` for the full rules.

## P7 — Manual invoice validation

- `workflowCreateInvoiceSchema` now **requires** `invoiceType` as a closed enum
  (`LISTING_PAGE` / `MINIWEBSITE` / `PRODUCT_POSTING`); free-text type input is
  rejected with **400**.
- `InvoiceWorkflowService.create()` derives the canonical project name and
  service type from `invoiceType` (via `INVOICE_TYPE_TO_PRODUCT_NAME`), and
  stores `invoiceType`, `gmId`, and `autoGenerated: false` for manual invoices.
- Route guards swapped to `requireManualInvoiceCreator()`:
  - Sales roles allowed; **Service Executive only when**
    `serviceExecutiveCanCreateManualInvoice` is `true` in config (otherwise
    **403**); admin override is allowed and audited.
- The legacy `POST /api/account/invoices` path was minimally hardened with the
  same role gate (`extraAllowedRoles: [ACCOUNT_MANAGER]`). **Documented gap:**
  this legacy path writes to a separate `invoices` table, not the canonical
  `product_posting_invoices`; full migration is out of scope for this stage.

See `INVOICE_TYPE_AND_APPROVAL_RULES.md` for the full rules.

## P8 — Approval completeness

- `assertApprovalReadiness(invoice, stage)` is called before both
  `PENDING_HOD → PENDING_ACCOUNT` and `PENDING_ACCOUNT → APPROVED`. An invoice
  missing a customer, a positive amount, or a type/service/project is rejected
  with **400 `INCOMPLETE_INVOICE`** listing the missing fields.
- On approve, the actor + timestamp are recorded: `hodApprovedBy/At` (HOD stage)
  and `accountsApprovedBy/At` (Accounts stage).
- On reject, `rejectedBy/At` are recorded; the existing required rejection reason
  is unchanged.
- Already-approved / already-rejected invoices cannot be re-approved (existing
  transition map still enforces stage validity).

## Schema (runtime, additive)

`npm run db:push` is broken repo-wide on a pre-existing FK type mismatch, so
schema changes are applied at boot via **idempotent runtime DDL**
(`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`) in `ensureInvoiceStage4Schema()`,
called from the boot path. New columns on `drm.product_posting_invoices`:

- `gm_id`, `invoice_type`
- `auto_generated`, `generated_by`, `generated_at`, `generation_event`
- `hod_approved_by`, `hod_approved_at`
- `accounts_approved_by`, `accounts_approved_at`
- `rejected_by`, `rejected_at`

Plus a partial unique index on `(gm_id, invoice_type)` where
`auto_generated AND gm_id IS NOT NULL` to guarantee idempotent generation.
All additions are non-destructive; corresponding Drizzle column defs were added
to `shared/schema.ts` (types only).

## Frontend

- `product-posting-sales-widget.tsx`:
  - Free-text "Project / Service Name" input replaced with an **Invoice Type
    dropdown** sourced from the shared constants; the create mutation now sends
    `invoiceType`.
  - The **New Invoice** button is hidden for roles not permitted to create a
    manual invoice (mirrors the backend policy).
- `product-posting-approvals-widget.tsx`:
  - Approval cards show invoice **type** and **company**, and flag
    auto-generated invoices.
  - **Approve is disabled** for invoices the backend would reject as incomplete
    (missing customer / amount / type), with the missing fields shown inline.
  - Rejection still requires a reason; queues refresh after each action.
