# Invoice Type & Approval Rules (Patch 5 — Stage 4)

Authoritative rules for **manual invoice creation** (P7) and **HOD/Accounts
approval completeness** (P8) on the canonical invoice system
(`drm.product_posting_invoices` + `server/services/invoice-workflow.service.ts`).

---

## 1. Invoice type is a closed enum (no free text)

Every canonical invoice has a **type** drawn from a fixed set. Free-text type
input is no longer accepted.

| Enum value        | Canonical product / project name |
| ----------------- | -------------------------------- |
| `LISTING_PAGE`    | Listing Page                     |
| `MINIWEBSITE`     | Alibaba Minisite                 |
| `PRODUCT_POSTING` | Alibaba Product Posting          |

- Source of truth: `INVOICE_TYPES` / `INVOICE_TYPE_VALUES` /
  `INVOICE_TYPE_TO_PRODUCT_NAME` in `shared/gm-sales-constants.ts` (shared by
  client and server).
- On create, the canonical `projectName` and `serviceType` are **derived** from
  `invoiceType`; callers do not hand-type them.
- An unknown / missing / free-text type is rejected with **HTTP 400**
  (`workflowCreateInvoiceSchema` requires the enum).

## 2. Who may create a manual invoice

Enforced by `requireManualInvoiceCreator()`:

| Role                  | Manual invoice allowed?                                   |
| --------------------- | -------------------------------------------------------- |
| Sales Executive / Sales Manager | Yes                                            |
| Admin                 | Yes (override is audited)                                 |
| **Service Executive** | **Only if** `serviceExecutiveCanCreateManualInvoice === true` in config; otherwise **403** |
| Everyone else         | No (**403**)                                              |

- The config flag `serviceExecutiveCanCreateManualInvoice` defaults to `false`.
- Manual invoices are stored with `autoGenerated: false` and land in the
  **HOD queue** (`PENDING_HOD`).

### Frontend mirror

- The **New Invoice** button in `product-posting-sales-widget.tsx` is hidden for
  roles not in the permitted set (`admin`, `sales_executive`, `sales_manager`),
  read from the session role. The server remains the source of truth; the UI
  hiding is a convenience layer. The sales widget is not a Service Executive
  surface, so the config-gated Service Executive case is enforced server-side.

### Legacy gap (documented)

`POST /api/account/invoices` is a **separate legacy path** that writes to a
different `invoices` table (not `product_posting_invoices`). It has been
minimally hardened with the same role gate
(`requireManualInvoiceCreator({ extraAllowedRoles: [ACCOUNT_MANAGER] })`), but a
full migration onto the canonical table is **out of scope** for Stage 4.

## 3. Approval completeness (no approving incomplete invoices)

`assertApprovalReadiness(invoice, stage)` runs before each approval transition:

- `PENDING_HOD → PENDING_ACCOUNT` (HOD approve)
- `PENDING_ACCOUNT → APPROVED` (Accounts approve)

An invoice is **incomplete** (and approval is blocked with **400
`INCOMPLETE_INVOICE`**, listing the missing fields) when any of these is true:

- no `customerId`,
- `amount` is not greater than `0`,
- none of `invoiceType` / `serviceType` / `projectName` is set.

### Audit actors + timestamps

- HOD approve sets `hodApprovedBy` / `hodApprovedAt`.
- Accounts approve sets `accountsApprovedBy` / `accountsApprovedAt`.
- Reject sets `rejectedBy` / `rejectedAt`; a **rejection reason is required**
  (unchanged).
- Already-approved or already-rejected invoices cannot be re-approved (the
  existing transition map still governs stage validity).

### Frontend mirror

`product-posting-approvals-widget.tsx` shows the invoice **type** and
**company**, flags auto-generated invoices, and **disables Approve** for any
invoice the rules above would reject — showing the missing fields inline. This
mirrors the backend check; the server still enforces it on submit.
